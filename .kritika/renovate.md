This is a Renovate dependency update. The question is whether merging it is safe: whether the new version breaks what this repository sets for the package, or changes the cluster whatever it sets. Answer it in this order and submit once you can.

First, read the release notes for each version between the old and the new with gh, or the changelog when there are none; the pull request body often already includes them. When gh shows no release for the new version and the upstream repository has no changelog file, the notes are on a website you cannot reach: say so in the summary and go on to the second step with the diff and the rendered changes. Open the compare view or an upstream documentation file only to settle one specific question the notes leave open, such as whether a flag this repository passes was renamed or removed, never to read the whole compare: do not download a compare, commit or pull request as a .diff or .patch. Do not read the package's source code (Go, Python, C++, TypeScript and the like), not one file and not as a file's patch from the compare API: what changed comes from the release notes, changelog, documentation, the chart's values, schema and templates, and the rendered diff.

Every command's output stays in your context for the rest of the review, so ask for small answers. Save an upstream file with `curl -sL -o <file> https://raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>` and search it with rg rather than printing it (read_file and grep read only this repository, not saved files); the gh contents API returns it base64-encoded. Filter gh output with --jq, and never list all tags, paginate a compare or fetch every release. Review the head you were given: do not look up other pull requests or this one's live state on GitHub. Renovate pinned the tag and digest: do not fetch registry tokens, manifests or image config.

Second, read what this repository sets for the package: the values, args, flags and env in the files the diff touches. Report each breaking change, removal, rename or changed default that touches one of those settings. For a chart, a changed default matters most where the repository sets nothing: report a new default that changes what runs, such as a replica count, a PodDisruptionBudget or other resource the chart stops or starts rendering, resources, probes, or a component turned on or off. The chart's values.yaml and values schema at both versions answer this. A default you read changing in values.yaml is verified there: it needs no confirmation from templates, schema, documentation or source. A template behind a value that is off by default and that the repository does not set does not render and needs no reading. For an image, a changed default counts only when the release notes name it.

Also report, whatever the repository sets, a change that reaches the cluster on its own or must be acted on before merging: RBAC or other permissions that widen, a new privileged, host path or host network setting, a newly required value, CRD or migration step, a raised minimum Kubernetes version, or the removal of an API the repository uses. For a chart, konflate's rendered diff shows these. A Role or ClusterRole that gains rules there is an important finding of its own: report it as the permission change, even when a value could narrow it. Any other change to something the repository does not set is not a finding and needs no further search.

Severity: a change of the kinds in the paragraph above is important at least, because a review with nothing important approves the pull request. Otherwise, blocking or important means merging as it is breaks something this repository runs, or needs an action before or with the merge. Anything else you would mention, such as an improvement, a follow-up, or something that does not reach the cluster until another change lands, is a nit or belongs in the summary.

The work is finite. For an image or application update it is the release notes matched against the args, flags and env the repository passes, about ten commands. Release notes list what was removed, renamed or changed: a flag or setting they do not mention is unchanged. Do not compare documentation, flag lists or metrics between versions, and leave the upstream build and release pipeline, this repository's Renovate config and its alerting out of the review. For a chart it is the release notes, what the repository sets, the chart's values.yaml and values schema at both versions and the rendered diff, or, when konflate does not track the pull request, the chart templates the compare lists as changed. Application settings the chart passes through, such as a config file in the values, are checked against the release notes and changelog, not the application's source. Submit once you have matched those against each other; that is the whole review, and most updates need about fifteen commands for it. Database or storage migrations that the application runs itself, and code changes behind a setting the repository does not use, are not findings and need no reading. Give a question the notes leave open at most two more commands; if it is still open after them, it is an open question for the summary, not a reason to keep reading. Report only what you verified. A concern you could not confirm is not a finding: name it in the summary as an open question. When you are told to submit, submit what you have on those terms.
